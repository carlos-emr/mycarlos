# myCarlos threat model

- **Status:** Durable-vault implementation complete; independent review and release gates open
- **Version:** 0.3
- **Date:** 2026-10-21
- **Initial platforms:** Windows, macOS, Android, and iOS
- **Deferred platform:** Linux, pending review of the documented `glib` backport and device/release validation
- **Data restriction:** Synthetic files only; this model does not authorize PHI use

## Purpose

This document identifies what myCarlos must protect, the trust boundaries an attacker may cross,
credible failure and abuse cases, and the controls and tests required before the application stores
patient records.

The native Tauri application includes the synthetic-data durable-vault slice described in
[`VAULT_FORMAT.md`](VAULT_FORMAT.md); the browser demo remains session-only. Implemented controls
are marked below, but they must not be read as approval for PHI or production use.

## Scope

The model covers:

- vault creation, locking, unlocking, and recovery;
- local PDF import, encrypted storage, viewing, and hiding (never deletion, #71);
- the React webview, Tauri IPC commands, Rust core, and operating-system services;
- local metadata, thumbnails, temporary files, logs, and crash artifacts;
- the portable encrypted backup, and future multi-device enrollment and synchronization;
- future CARLOS document handoff and provenance verification, including pickup from the portal
  the patient links, myCarlos's first network use (carlos-portal #41);
- the AI helper (#72): an on-device anonymizer with a preview and a text-file export (built), a
  local model in a sandboxed helper and the answers it gives (the runtime, the model download and kept answers on main, #218, #219, #212); its
  only network use is the model download, on a click (AI-08); and
- build, signing, updating, and third-party dependencies.

It does not approve a PDF renderer, synchronization service, analytics provider, CARLOS
protocol, or AI model or model runtime. The current encryption and passphrase-only recovery
design is implemented but awaits independent review and target-device verification.

## Security and privacy objectives

1. A locked or powered-off device does not disclose document contents or sensitive metadata.
2. A cloud or synchronization provider cannot decrypt patient records.
3. Encryption and recovery keys never enter the React renderer, logs, analytics, or crash reports.
4. Untrusted documents cannot obtain native privileges or escape the document viewer.
5. Native commands expose the minimum capability required and authorize every operation.
6. Tampering, corruption, rollback, incomplete writes, and false provenance are detected.
7. Nothing a patient hides is lost: documents are never deleted, only hidden, and stay encrypted
   and restorable (#71, decided 16 October). A whole-vault reset or a restore sets the vault aside,
   whole and encrypted, instead of erasing it; only the patient, by hand, deletes one. On Android
   and iPhone that is possible only by clearing the app's data or uninstalling it, which removes
   every vault; this limit is accepted (decided 19 October), so starting again is offered only on
   the unlock screen, not in Security, and the documents say so.
8. Security failures are explicit and fail closed without silently destroying recoverable data.
9. The patient can understand when a record is verified, unverified, locked, backed up, or hidden,
   and that hidden documents are kept.
10. No production patient data is used until the applicable controls and tests pass review.

## System and trust boundaries

```mermaid
flowchart LR
    Source[CARLOS, email, Files, or share sheet]
    Picker[OS picker or share target]
    UI[React webview]
    Core[Rust vault core]
    Viewer[Isolated document viewer]
    Keys[Keychain or Keystore]
    Vault[Encrypted local vault]
    Backup[Portable backup file; future untrusted sync service]
    Portal[Linked portal mailbox; planned, carlos-portal #41]
    Model[Local model helper; #72, #218]
    Export[Anonymized text file; #72 part B, desktop only]
    ModelHost[Model download host and its CDN; #72, #219]

    Source -->|untrusted document and metadata| Picker
    Picker -->|native handle or URI| Core
    UI -->|typed commands using opaque IDs| Core
    Core -->|sanitized render payload| Viewer
    Core -->|wrapped key operations| Keys
    Core -->|authenticated ciphertext| Vault
    Vault -->|ciphertext and privacy-minimized metadata| Backup
    Core -->|device-signed requests, to the linked portal only| Portal
    Portal -->|packages sealed to this device, signed by the clinic| Core
    Core -->|text of one document, for the preview, desktop only| UI
    UI -->|final anonymized text and preview ticket, for the save| Core
    Core -->|text of one document, bounded, no keys| Model
    Model -->|answer text only| Core
    ModelHost -->|public model file, on a click, size and SHA-256 checked| Core
    Core -->|anonymized text after the preview and a native re-check| Export
```

The important trust boundaries are:

| Boundary | Rule |
| --- | --- |
| External source to OS picker | Selection is user intent, not proof that a file is safe or authentic. |
| React webview to Rust | Treat the renderer as untrusted. Validate command, state, identity, size, and object ID in Rust. |
| Rust to OS key storage | Store only the minimum wrapping material and bind access to the intended application/device policy. |
| Rust to local storage | Durable document content, metadata, indexes, and derived artifacts must be authenticated ciphertext. |
| Vault to viewer | Decrypt only after unlock; constrain viewer privileges and prohibit uncontrolled network or native access. |
| Device to backup/sync | Treat the service and transport endpoint as unable to keep plaintext confidential. |
| CARLOS to myCarlos | Verify origin, integrity, freshness, and intended recipient before showing verified provenance. |
| Camera to webview | Video only, asked for after the patient chooses to use the camera, and stopped when the photo is taken or the dialog closes. The frame stays in memory; Rust checks and cleans the JPEG before it is encrypted. |
| myCarlos to linked portal | Once linked, the portal is a mailbox, not a trusted source: it holds packages it cannot open (at linking, the clinic keys it returns are trusted on first use; NET-02). Connect only to the portal the patient linked, sign every request with that link's device key, and verify every package before anything is saved (NET-01 to NET-03, DEL-01 to DEL-06). |
| Vault to the AI helper's model (#72; the reader and the helper on main, #217, #218) | The model runs in a sandboxed helper mode of the app (`--mycarlos-model-helper`) with no vault keys, no network and no file access; it gets the checked model as a sealed memfd (Linux) or by path with writers denied (Windows) (AI-04, AI-07). It receives one document's pages and returns grammar-bound text only; its answer is never treated as instructions, links or markup (AI-05). |
| myCarlos to the model's download host (#219) | On a click only: HTTPS to the catalogue entry's pinned address and its CDN, no other host, no cookies or credentials. The file is public and holds no patient data; the host sees the computer's IP address, the time and which file; the size and SHA-256 are checked before the file is used (AI-04, AI-08). |
| Anonymized text to the patient's chosen AI service (#72 part B, desktop only) | myCarlos does not send it. The patient saves a plain text file after a preview and takes it where they choose; once saved, it is outside the vault's protection, like a readable copy, and what the receiving service learns or keeps is up to it (AI-01 to AI-03, AI-08, AI-09). |

## Assets

| Asset | Harm if compromised |
| --- | --- |
| Decrypted documents | Direct disclosure of personal health information. |
| Document titles, tags, dates, thumbnails, and provider names | Sensitive diagnoses and care relationships can be inferred without opening a PDF. |
| Vault data-encryption keys | Complete or object-level vault disclosure. |
| Passphrase-derived and recovery key material | Offline vault compromise or permanent patient lockout. |
| Device-bound wrapping keys and biometric authorization | Unauthorized unlock on a stolen or shared device. |
| Encrypted vault and manifest | Deletion, corruption, rollback, traffic analysis, or offline guessing. |
| CARLOS provenance manifest and signature keys | Forged or misattributed clinical documents. |
| Per-link device keys and pinned clinic keys | Reading deliveries meant for this device, posing as the device to the portal, or trusting a forged clinic. |
| Linked portal address and recipient ID | Tying the device to a clinic; the network learns that this device uses that clinic's portal. |
| Backup and synchronization state | Cross-device disclosure, rollback, duplicate resurrection, or data loss. |
| Logs, crash reports, clipboard, notifications, and OS snapshots | Secondary disclosure outside the vault. |
| Signing and update credentials | Distribution of a malicious application update to every patient. |
| Anonymized text and its exported files (#72 part B, desktop only) | A missed detail re-identifies the patient or someone else; the file is a plaintext copy outside the vault. |
| AI answers (#72; kept in the vault with #212) | They disclose health information as the document does, and a wrong answer may be trusted as medical advice. |
| The local model file and the model list built into the app (#72, #219) | A swapped model could exploit the model runtime or give deliberately misleading answers. |

## Threat actors and assumptions

Credible threat actors include a finder or thief of a device, another user of a shared computer,
malware with ordinary user privileges, a malicious document sender, a compromised website or deep
link, a compromised backup provider, a compromised or malicious portal operator, a network attacker
between the device and the portal, a supply-chain attacker, an attacker controlling a future
synchronization account, a sender who writes instructions into a document to steer an AI model
(prompt injection), and the AI service a patient gives exported text to (#72).

The following limits must be communicated honestly:

- The vault must protect a lost locked device and copied vault files.
- The vault must protect records from the backup or synchronization operator.
- The application cannot guarantee confidentiality while records are visible on a device whose
  operating system or privileged account is already fully compromised.
- OS key stores reduce key-extraction risk but do not replace a vault encryption and recovery model.
- myCarlos can verify that a package was signed by a recognized clinic; it cannot guarantee that the
  clinical content entered by that clinic is medically correct.
- Removing identifying details from text is never perfect, and an AI model can be wrong. myCarlos
  can show both to the patient (a marked preview, a label on every answer) but cannot rule them
  out. An AI service the patient is signed in to knows who they are, whatever was removed (#72).
- Availability after total device loss depends on the recovery and backup design. Until those are
  implemented and tested, the application must not imply that records are recoverable.

## Risk scale

Risk is initially qualitative because usage, deployment, and recovery designs are not final.

- **Critical:** plausible compromise or irreversible loss of most of a patient's vault, signing
  infrastructure, or recovery authority.
- **High:** disclosure or unsafe modification of one or more records, or escape from an untrusted
  document into native application privileges.
- **Medium:** limited metadata disclosure, local denial of service, or a weakness requiring another
  significant compromise.
- **Low:** minor impact with narrow prerequisites and straightforward recovery.

Residual risk must be rescored after a control is implemented and tested. “Planned” controls do not
reduce current risk.

## Threat register

| ID | Risk | Threat and impact | Required controls | Verification | Status |

| KEY-01 | Critical | An attacker copies the vault and guesses the patient passphrase offline. | Unique salt; reviewed memory-hard password KDF; platform-benchmarked work factor; random vault key wrapped by the derived key; no password verifier that makes guessing cheaper. | Password-cracking cost review and tests against copied vault fixtures on every target class. | Argon2id, 15-character minimum, local common-pattern/context screening, and benchmark harness implemented. The strength floor is zxcvbn score 3 (an estimated 10^8 to 10^10 guesses), kept on purpose: with the 15-character minimum many passphrases are expected to score higher (not measured), and a higher floor would refuse passphrases a patient can remember, which pushes towards writing them down or reusing one. At the floor itself, one Argon2id run per guess (64 MiB, 3 passes, 4 lanes) puts a copied vault within days of a well-equipped attacker, an estimate that has not been measured. Guessing through the app on the device waits after five wrong tries in a row (5 seconds, 5 more for each further one, to a minute), counted apart for unlocking (with the passphrase checks made while the vault is open), the recovery key and backups, and kept beside the vault across restarts; it does nothing against a copied vault or backup, where only the key derivation's cost applies, and whoever can delete its file, make it unwritable, set the clock forward or before 1970, or run several copies of the app at once undoes or weakens it. Production breach corpus, physical results, a measured guessing rate and the independent review of this floor open |
| KEY-02 | Critical | Recovery becomes a universal backdoor or is easier to attack than the passphrase. | Patient-controlled recovery only; no vendor or clinic recovery secret; high-entropy recovery kit verified at setup. A found kit opens the vault, so the kit carries no patient or document names and the key can be replaced. | Recover on every target with the kit and confirm the service cannot decrypt. | 128-bit recovery-key envelope (header format 2), typed-back verification before it is stored, replacement after which the old key no longer opens the current headers (the master key is not rotated, so it still opens earlier copies of them; the setup asks why the key is replaced: if its kit may have been lost or seen, the app guides the patient to save a new backup and then delete older ones, or to keep them while the vault cannot save one; otherwise it says to keep the old kit safe or destroy it on purpose), a short label that is not secret on the kit and in Security so that the current kit can be told from others, offered again when a vault without a key is unlocked, at most once a day (the hour of the last offer is kept in the app's settings on the device and names no vault; as an offer that can be left, which makes and shows no key until asked, and says to go on only when nobody else can see the screen), and recovery with a new passphrase implemented, with setup offered first when a vault is created (Escape or "Lock vault and finish later" first asks whether to discard the key on screen; confirming cancels the unfinished key and locks the vault, and Escape in that question goes back to the setup; the vault shows a banner until a key is set up), a saved or printed plain-text kit, and recovery from the unlock screen; on-device recovery drills and review open |
| KEY-03 | High | Keys leak into the renderer, logs, crash dumps, swap, or long-lived memory. | Perform key operations in Rust/native code; never serialize raw keys over IPC; redact diagnostics; minimize key lifetime; use protected memory/zeroization where supported. | Instrument IPC and logging, force crashes, inspect artifacts, and review memory-handling paths. | Rust boundary, direct zeroizing key buffers, and streaming-I/O cancellation implemented. Two deliberate exceptions. A new recovery key is returned once over IPC so the patient can write it down; the renderer keeps no reference to it once the setup dialog closes, and adds it to the page for printing only while it prints (printing hands it to the operating system's print service). A recovery key typed by the patient (on the unlock screen, or to open a backup) travels the other way, like a passphrase, and is wiped natively; on the unlock screen, and in the restore form, it waits in that screen's state until it is used, the app is hidden, or five minutes pass untouched. The renderer cannot wipe either from its memory. At first setup, the new passphrase being typed also crosses IPC before Create, to `vault_passphrase_rules`, so that the setup checklist ticks by the vault's own rules (#69): it is sent once typing has paused for 300 ms and never while Create runs, judged natively by the same function as Create, and wiped there as the command returns (its request zeroizes on drop, as `vault_create`'s does); nothing of it is logged or kept, no error echoes it, and the answer is three booleans, never a score or a hint. Shown as text in that screen, it is kept from spell checking, autocorrection and autocapitalization, as every shown secret is. A saved kit holds the key in plain text by design, written natively only to a file the patient picks; for a filesystem path it is refused inside the vault home, private to the user (on Unix) and replaced atomically, while a document provider (Android) is written directly. Blocking-provider, crash and artifact review open |
| KEY-04 | High | Biometric unlock bypasses the intended passphrase policy or survives device-account changes. | Biometrics authorize use of a device-bound wrapping key; passphrase/recovery fallback; invalidate as appropriate after biometric or device-credential changes. | Test enrollment changes, fallback, repeated failures, device restore, and copied application data. | Design selected; implementation open |
| KEY-05 | High | A stale key envelope or vault manifest is restored to bypass deletion or revive old access. | Authenticate and version key envelopes and manifests; define rollback detection and device reconciliation. | Restore older fixtures and confirm safe detection rather than silent acceptance. | Changing the passphrase, like replacing the recovery key, wraps the same master key again and does not change it: the earlier passphrase still opens any earlier copy of the vault's headers (a device backup, a copied folder, a saved backup file), and the master key it yields decrypts the vault as it is now and as it will be. The only remedy is a new vault, which the app does not guide and which loses folders, profiles and dates (the steps are in `VAULT_FORMAT.md`, "Known limits"); restoring an earlier backup into it brings the earlier master key back. The Change passphrase screen states the limit and tells the patient to ask for help before erasing; rotating the master key is not implemented, and is planned for after the first release: until then an old passphrase or recovery key, with a copy of the vault's headers made while it was in use, keeps opening the vault as it is now. Portable backup restore detects a copy of the same vault that differs from the backup, a different vault, or a vault it cannot read to tell, and requires explicit agreement, repeated in a trusted native dialog that says what would be lost, before replacing it (a restore brings back the documents, passphrase and recovery key the backup was made with); rollback of externally restored slots and device reconciliation open |
| KEY-06 | High | The patient loses the passphrase and permanently loses the only copy of the record. | Patient-held recovery kit, portable authenticated backup, rotation, and explicit custody warnings. | Recovery, rotation, lost-kit, and historical-backup drills using synthetic data. | Permanent-loss warnings, the recovery key and its kit, and the portable encrypted backup implemented; recovery and restore drills on devices open |
| IMP-01 | High | A selected path, URI, symlink, or replaced file makes the app import a different file than the patient chose. | Open once through native code; use handles/content URIs where available; reject links and special files; avoid check-then-open logic; never accept renderer-supplied filesystem paths. | Symlink, race, content-provider, shared-directory, and path-manipulation tests per platform. | Local links/special files rejected, Unix no-follow and Windows reparse-point handle checks implemented, and renderer paths excluded; ordinary-file replacement races/content-provider testing open |
| IMP-02 | Critical | A crafted PDF exploits the parser and reaches vault keys or native commands. | Sandboxed capability-free rendering helper with no vault keys or network; bounded rendered output; prompt renderer updates. | Malformed corpus, known parser regressions, network observation, and attempted IPC/native access from the renderer. | Helper for unlocking (#54) and viewing (#48): parsing runs in a separate process with no vault keys, and myCarlos itself is not dumpable on Linux, so a helper cannot read its memory. The helper is sandboxed before it reads anything (#63): on Linux a seccomp allowlist (stdin, stdout and stderr, non-executable memory, ending; no open, socket, exec, ptrace or signal to another process) is required, with Landlock denying every file and network right on top where the kernel has it; on macOS `sandbox_init` with a deny-all profile; on Windows myCarlos starts it in a no-capability AppContainer (no network, no user files, low integrity), inheriting only its two pipes, inside a job object (memory, one process) it joins before it runs, and the helper checks its token. The helper's only environment is a placeholder LOCALAPPDATA (C:\mycarlos-none), which Windows needs to start an AppContainer: it is not a real folder, and no user variable is passed. If the sandbox cannot be set up the helper reads nothing and the patient is told the document cannot be opened safely on this system. Resource limits (CPU, memory, file size, processes, descriptors; macOS footprint checked by myCarlos) and a 30 s watchdog bound cost. Per-platform tests in CI try to read and write a file, connect, and start a program from inside it, against a control without it. Phones do not run it. Not covered: kernel exploits, side channels |

| CAM-01 | High | The camera turns on without the patient knowing; a photo carries where it was taken (GPS), the camera, or another picture; or a photo is left readable outside the vault. | Camera asked for only from the camera dialog, after the patient's choice, for video and never sound; on Linux and Windows the native permission handlers allow the camera for the app's own pages only and refuse every other request (on Android and iOS, Wry's own handlers grant the page's request; see below); every track stopped when the photo is taken, the dialog closes, the vault locks, or the window is hidden. The JPEG is drawn and encoded by the app's own canvas, then checked and cleaned in Rust before it is encrypted: one 8-bit baseline or progressive frame of at most 8,192 pixels a side, at most 25 MB, with every APP1–APP15 segment (Exif and GPS, XMP, ICC, IPTC, maker data), comments, any JFIF thumbnail and anything after the end marker removed, by walking the markers, never decoding pixels. The photo is stored through the import path, with its encryption, verification and duplicate check; nothing is written to disk in plain form. | Rust tests with a GPS-tagged Exif block, XMP, ICC, IPTC, comment, thumbnail and appended-video JPEG built from a real canvas JPEG; refusal of malformed, other-coding and oversized JPEGs; component tests with a fake camera for every way the camera stops; browser test with Chromium's fake camera and a refused camera. | Desktop implemented (Linux WebKitGTK: media stream turned on, user-media requests for video only allowed, everything else refused; Windows WebView2: the camera allowed for the app's pages, every other kind refused, also when a request cannot be read; macOS: Wry grants capture and macOS asks with `NSCameraUsageDescription`; no microphone reason is declared, and the app never asks for sound; a signed hardened-runtime build will also need the `com.apple.security.device.camera` entitlement). A document's details ask only whether its file starts as a JPEG, reading its first bytes; the photo is decrypted and sent to the webview only when the patient chooses View photo, and dropped when the view closes. The webview's own copies of camera frames, the canvas and the encoded JPEG are freed but cannot be overwritten by the app (it zeroes the bytes it holds and clears the canvas), and neither is the IPC layer's copy of the request body. The camera dialog keeps a photo's JPEG under 4 MB, lowering its quality and then its size, so that copy stays small. A photo is shown by the main webview's own image decoder, from a `data:` URL the vault returns after the same checks; viewer isolation remains as for IMP-02. When Tauri uses its postMessage channel instead of its custom protocol (always on Android, and on Windows once the custom protocol has failed in a session), the photo's bytes arrive as a JSON array of numbers that Tauri has already parsed into its own value before the app's handler runs: that copy, several times the photo's size, is neither overwritten nor size-limited by the app, which counts the array against the 25 MB limit only before copying it. Phones (D97), written but not yet run on a device: the same dialog, back camera first, and the same canvas JPEG and Rust cleaning. Android: the manifest declares the camera permission (not required, no microphone), and a build without it fails; Wry's web chrome client asks Android for that permission when the page asks for video, then grants the page's request (it does not check the origin or the kind itself: only the app's own pages load, and they ask for video only). iOS: Wry grants WebKit's capture request, of any kind, and plays video inline, and iOS asks with `NSCameraUsageDescription` from `Info.plist`; no microphone reason is declared, so a microphone request would end the app, and nothing asks for one. Android also declares the autofocus the camera permission implies as not required, so Google Play does not leave out devices without it. While the phone asks whether myCarlos may use the camera, the lock on hiding the app is held as for a file picker (UI-03). Real cameras on Windows, macOS, Linux, Android and iOS, the Android "don't ask again" path and iOS's custom-scheme page counting as secure for the camera open |
| IPC-01 | Critical | Compromised React code invokes privileged Tauri commands to read, overwrite, or erase data. | Keep narrowly scoped capabilities; commands accept bounded opaque vault IDs rather than paths; authorize lock state and operation in Rust; require trusted native confirmation for whole-vault reset; no generic read/write/execute command. | Enumerate generated permissions and fuzz every command while locked and with invalid IDs. | Opaque application commands declared in the build manifest and granted only to the main window, collection bounds, no webview plugin/core permissions, native reset confirmation (and native confirmation before a restore replaces a vault, and before a new recovery key replaces the one a vault has), arbitrary IPC deserialization properties and locked/unknown-ID operation matrix implemented. The setup checklist's `vault_passphrase_rules` reads and writes nothing: it is refused once a vault exists, open or locked, so it cannot be used to test guesses against a vault, and it answers three booleans only (#69). Accepted for now: changing the passphrase and hiding documents have no native confirmation, so compromised page code, which sees the passphrase as it is typed, can change the passphrase to one of its own, which locks out a patient whose vault has no recovery key (a vault that has one still opens with it, if the key was set up while the page code was sound: replacing it is confirmed natively, though giving a vault its first key is not, and the confirmation cannot show which key is being stored, so page code that showed the patient a key of its own making during a setup would leave the vault with a key only it holds; a kit saved to a file is written natively and holds the true key), or hide every document one by one (or those shown as damaged), which takes them out of view but deletes nothing (#71): Restore brings each back. Whether these get a native confirmation is an open product decision. While that confirmation is open the automatic lock is held off, as it is for a file picker, for no longer than a picker's hold, and the lock on hiding the app waits with it. The first button of each native confirmation, which is the default Enter/Return target on Windows and macOS, keeps things as they are; the button that goes ahead is the second, and only it counts as agreement. Which button Enter, Space and Escape press rests on how each platform lays a dialog out. The dialogs are given the app's window. By the dialog library's source and the platforms' own documentation, on Windows the first button is the default and Escape and closing cancel, and on macOS a native main-thread sheet of the window assigns Return to the first button and Escape to the third, with no shortcut for the second, independently of their translated titles. Only a supported language tag crosses IPC; native code selects the bundled warning and button text and refuses blank or colliding labels. On Linux the dialog sets no explicit default and takes no notice of the window, so focus and keyboard behavior depend on the desktop configuration. Automated native tests check cancellation and deliberate confirmation on Windows and Linux; platform coverage and remaining device checks are tracked in TESTING.md. Explicitly activating the second button still goes ahead. Native harness fuzzing remains |
| IPC-02 | High | XSS or remote content gains the privileges of the main application webview. | Bundle UI assets; restrictive CSP; no remote scripts; sanitize rendered text; isolate document content; review navigation and deep links. | CSP tests, dependency review, injected markup fixtures, and blocked-network assertions. | Production CSP/dev separation, prototype freezing, and hostile-metadata/off-origin browser regression implemented; the window refuses to go anywhere but this platform's bundled pages (and the development server in a development build), and on desktop refuses to open another window, with the rule unit-tested. ## Secure Vault v0.1 security gate

The synthetic local-vault vertical slice is not complete until all of the following are demonstrated:

- [ ] A threat-model reviewer and application owner approve the scoped risks and assumptions.
- [ ] D-01 through D-05 are decided and recorded.
- [ ] A synthetic PDF is encrypted before entering application-controlled durable storage.
- [ ] Document content, title, provider, date, thumbnails, and search index are unreadable while locked.
- [ ] Raw keys never cross Tauri IPC or appear in logs and crash artifacts.
- [ ] The vault can be closed, restarted, unlocked, rendered, and deleted on each initial platform.
- [ ] Import interruption at every persistence boundary leaves either the previous valid state or a
      detectable, safely recoverable incomplete state.
- [ ] Malformed and hostile PDF tests cannot access native commands, vault keys, or the network.
- [ ] Wrong-passphrase, corrupted-object, rollback, low-disk, and lost-key paths fail explicitly.
- [ ] Backgrounding and inactivity conceal content and require reauthentication as designed.
- [ ] Storage and OS-backup inspection finds no plaintext canaries.
- [ ] No unresolved critical/high vulnerability affects a shipped runtime dependency.
- [ ] Windows, macOS, Android, and iOS checks pass; no release workflow produces a supported Linux
      artifact before review of the `glib` backport and Linux device/release validation.

Passing this gate permits the next synthetic-data development phase. It does not by itself authorize
real patient data, a patient pilot, CARLOS integration, or production release.

### Signed-PDF import analysis draft (#101)

The import pipeline now invokes a bounded signature analysis without changing stored
original bytes or the unverified source label. Main checks cryptography and clinic pins
before a password reaches the confined extraction stage. The current signed CMS digest
binds exact manifest bytes, including encrypted attachments; helper structure reports
alone grant no trust. Duplicate attributes, malformed OIDs, altered manifests, missing

## Authenticated portal link implementation (#55)

Every build includes the linking code; until 4 November 2026 it was selected by a
Cargo feature, `portal-linking`. A renderer value cannot change what is built. On
Android the native command refuses before generating keys, changing the vault or
making a request, until the platform verifier is integrated. This separate future branch includes held profile
format 4 and reserves manifest format 5; it does not authorize that migration for
the current demo.

Linking sends only the v1 code, a patient-edited generic device name, two fresh
per-link public keys and their possession assertion to the HTTPS portal address
the patient supplies. Portal SMS MFA authenticates the code's browser session;
myCarlos neither collects an MFA secret nor adds another authentication factor.
No URL from a PDF or manifest selects an endpoint. The native client uses only the
portal base path plus `/api/mycarlos/`, refuses redirects, bounds response bodies
and request duration, and never logs request, response, assertion or URL contents.
The production webview CSP and PDF helper network boundary remain unchanged.

Private link seeds and received pins are encrypted within the vault. Pending keys
are committed before the one-use code is sent; linked state is committed only
after response validation, with history. Network work releases the session lock;
a session generation rejects any completion after locking, even after unlock.
A lost one-use response can leave a device registered at the portal without a
completed local link: this must be reported as incomplete, never guessed successful.
A recovery endpoint, live key refresh and signed-replacement statement are shared
v1 contract work, not an invented delivery v2. Their absence prevents claiming
the whole #55 key lifecycle or the send/pickup/delete flow complete.

### Private first-device pickup candidate (26 October 2026)

The same linking code now includes explicit mailbox checks and first-device
approval requests. All destinations remain the saved consented HTTPS portal.
The renderer receives redacted native summaries, never seeds, decrypted packages,
receipts or recipient IDs. Native code validates original signed package/PDF
bindings before an atomic custody transaction publishes original/display objects,
history, verification metadata and exact kept receipt. Receipt sending is a
separate step after that commit, with restart-safe exact-byte retry. A generic
HTTP 404 never settles a receipt. An uncertain commit preserves objects and
requires restart repair. Full-device fingerprints are public identifiers for
staff comparison, not approval credentials; only a bound clinic signature grants
native approval status. Historical proof verification cannot grant current trust
after signer revocation. Key refresh and broader approval/recovery flows remain
unfinished and defaults remain OFF. Linux FAKE interoperability and subprocess
crash checks do not establish Windows or live portal end-to-end behavior.

### Accepted residual risk: clinic keys trusted at linking (28 October 2026)

When a device links, myCarlos takes the clinic's signing keys from the portal
at the address the patient enters, over HTTPS, and trusts them for that link
from then on. Nothing outside that portal confirms them. A patient who links to
a look-alike portal, or whose linking is intercepted or answered by a
compromised portal, can therefore receive documents that show as Verified, as
coming from the clinic the portal names. This does not expose the vault's
contents, and nothing from the vault goes to that portal beyond what any linked
portal receives (NET-03). Ben accepted this risk on 28 October 2026 so that
myCarlos works with other EMRs' portals (NET-02, DEL-06). Possible later steps:
show the portal's address next to "Verified" and at linking, and a clinic-key
code checked during the staff fingerprint comparison.

Clinic code v1 (DEL-07) does not narrow this risk. A look-alike portal signs
its own challenges with the keys myCarlos took from it, so it can ask for staff
approval and accept the device itself (`verify_challenge` accepts either kind),
and a device with an open request already picks up what that portal sends
(`worth_asking`). What clinic code v1 does stop is the related DEL-07 case: the
clinic's real emailed code never matches on a device linked to a look-alike
portal, so it is never sent there and cannot approve a device at the real
clinic, and the patient is told to check the portal address.

## AI helper (#72: the export, the reader, the model runtime, the download and kept answers are built)

Issue #72 asks for an AI helper that explains a document in plain words. Ben's decisions
(29 October 2026):

1. **No cloud provider.** The "cloud" way is: myCarlos removes identifying details on the device,
   shows a marked preview that the patient can edit by removing more, and the patient saves the
   text as a plain text file and takes it to whichever AI service they choose. There is no
   provider, no key and no network call (AI-08).
2. **The export is a file save,** like "Save a copy", and is recorded in the history. Clipboard
   copy and a redacted PDF are later ideas. The text comes from the reader's own text extraction
   (`pdf_view.rs`, #48).
3. **Synthetic data only** until the pilot privacy review (#25).
4. **First tools:** a plain-words summary and "explain a term". Questions and filing come later.
5. **The local model** is chosen after a bake-off of small open models on synthetic documents
   (quality, speed, memory, licence).

The work lands in steps, each citing its threat IDs: the anonymizer, preview and export (part B;
AI-01 to AI-03); the bake-off report (part C, no app code); then the two tools behind a "model not
installed" state (part D: AI-05 to AI-07; AI-04 with the step that adds the model: the download and the add-a-file route, #219; the runtime, #218). AI-10 is
the text source for both, and AI-09 is a stated limit of the export. The patient-facing notice for
all of it is [`AI_HELPER_NOTICE.md`](AI_HELPER_NOTICE.md), in all seven languages.

This model does **not** cover:

- sending text to a cloud provider or a relay (the issue's first idea): that would add a host, a
  key and a data processor, and needs its own review (NET-01, AI-08);
- scanned pages, which have no text until on-device text recognition exists;
- phones: the PDF helper does not run there (IMP-02), so a phone can neither read a document's
  text nor run a local model, and neither the export nor the AI on this device works on a phone
  until a phone design is reviewed;
- macOS for now: the model helper is built for Windows and Linux only, and a Mac says "not available on this kind of computer yet" until #211;
- the later tools (questions to ask, filing suggestions).

Stated limits: removing details is never perfect (AI-01); an AI service the patient is signed in
to knows who they are, whatever was removed (AI-09); a local model can be wrong, and slow on an
ordinary computer (AI-05, AI-07); and because the model list is built into the app, a new or
updated model needs an app update, which reaches only patients who update (MASVS CODE-2).
