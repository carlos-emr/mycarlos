# Fresh-request MTP isolation fixture source

This distinct successor preserves the actual passed two-request synthetic check. A single model is loaded once; each of two requests independently constructs and destroys target context, draft context, MTP wrapper and batch. It reuses the authoritative V3 mechanics without clearing/reusing a context, saving a prefix or carrying native state between requests. The same fixed non-clinical input is used twice.

Root compiled and executed the private fixture successfully. Each request processed513 prefill tokens as512+1, committed8 answer tokens, naturally accepted3 draft tokens and performed1 explicitly forced accept0 prefix truncation followed by recurrent rollback/another decode. Exact committed token vectors, their diagnostic FNV-1a64 hashes and final target/draft positions matched across both requests. Causal attention was measured true. Internal microbatch counts remain source-derived, not observed internal traces. There were no natural rejections. These results do not qualify the production application, grammar, EOG handling, sandbox, quality or speed.

Memory was measured before construction, after each context, before wrapper/context destruction, and after destruction. Between the two post-drop observations, data increased24708KiB and RSS52924KiB. Two requests and these allocator-dependent measurements do not establish leak-free behavior. The fixture does not assert that memory returns to an exact baseline.

The data cap remains model bytes plus2GiB, context8192, logical batch512, target micro512, draft micro64 and3 threads. Each request is bounded to4 K1 rounds plus one final pending-token decode, at most8 answer commits (at most16 total). The internal alarm is170 seconds, requiring a separate180-second Root-owned outer budget including cleanup. Failed requests stop the loop; there is no hidden retry or model reload.
