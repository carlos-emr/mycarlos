# Frontend component coverage

Coverage is an opt-in developer check. It does not run during `npm test`, `npm run
check`, or a packaged application build. Rust coverage has a separate command and
denominator and a Python 3 prerequisite: see
[COVERAGE-RUST.md](COVERAGE-RUST.md).

Use the repository's Node version and locked dependencies:

```sh
npm ci
npx --no-install playwright install chromium
npm run test:coverage:frontend
```

The command runs all existing component tests in headless Chromium with one
worker. It keeps the normal component configuration, setup, and test timeouts.
The official `@vitest/coverage-v8` provider is pinned to the same version as
Vitest. Vitest starts coverage before importing the test and application modules;
this is not a profiler attached after test setup.
Update Vitest and its coverage provider together; their versions must match.

Run it from a checkout whose `node_modules` is a real directory, or allow Vite to
serve the link's real path (`server.fs.allow`). With `node_modules` symlinked to
another checkout, Chromium cannot fetch `@vitest/coverage-v8/browser` (Vite refuses
files outside the project root), every test file reports a prepare error, and no
report is written.

## What the percentage measures

The report covers hand-maintained TypeScript and TSX under `src/`, including
production files that no test imports. The explicit `coverage.include` pattern
keeps those files eligible for zero-hit reporting. Entry points such as
`src/main.tsx` remain in scope even when the component suite does not load them.

The exclusions are:

- Component test files and `src/test/` setup/helpers.
- Type declaration files (`*.d.ts`), which have no executable code.
- `src/i18n/locales/fluent/keys.ts`, generated by
  `scripts/generate-fluent-bindings.mjs`. This excludes its generated runtime
  lookups as well as its generated types. The metric therefore does not claim to
  cover every generated executable statement.

Dependency code, build output, CSS, Fluent catalogues, Rust, and platform-native
application behavior are outside this source denominator. Existing component
tests use their normal injected or mocked native bridges; this is Chromium
component coverage, not installed Windows, macOS, Android, or iOS coverage.

Statements, branches, functions, and lines each have their own covered/total
counts. A test pass count or a count of files imported is not a coverage
percentage. Do not combine this report with Rust or Portal percentages into a
single project percentage.

## Reports and reproducibility

The local, ignored `coverage/frontend/` directory contains:

- `coverage-final.json`: per-file source coverage data.
- `coverage-summary.json`: covered/total counts and percentages.
- `lcov.info` and the HTML report (`index.html`).

Each run cleans only that frontend report directory before collecting new data.
There is no upload service or percentage threshold. A failing test run exits
unsuccessfully and does not generate a coverage report; do not reuse an earlier
report as evidence for it.

When sharing results, record the full source commit, Node and Vitest/provider
versions, exact command, actual test results, and report files together. Check
that the report includes never-imported production files and that its source
paths and exclusions match this configuration. Coverage from a filtered or
sharded test run must be labelled with that scope; a shard's output alone is not
the full-suite result. Instrumentation adds time and memory to the normal run.
